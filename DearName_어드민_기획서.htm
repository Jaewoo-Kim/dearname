1. 문서 개요

1.1 목적

본 문서는 DearName 서비스를 안정적으로 운영하기 위한 운영자 전용 어드민(관리자) 사이트의 기능과 화면을 정의한다. 개발 착수 전 "무엇을, 왜, 어떤 화면으로 만들 것인가"에 대한 기준을 공유하는 것이 목적이다.

1.2 작성 배경

현재 DearName은 사용자용 서비스(작명/분석)는 동작하나, 운영자가 주문·매출·보고서를 확인하거나 관리할 수단이 전혀 없다. 유료 서비스를 지속 운영하려면 결제 내역 추적, 고객 응대(보고서 재발급), 매출 파악이 필수적이며 이를 위한 어드민이 필요하다.

1.3 문서 범위

본 기획서는 어드민의 1차 버전(MVP)을 다룬다. 기술 스택·아키텍처 등 구현 상세는 별도 문서 「어드민 사이트 구축 계획(admin_site_plan.md)」을 따른다.

1.4 용어 정의

용어의미

셀프 분석사용자가 직접 이름을 입력해 분석하는 무료/저가 상품

2. 추진 배경 및 문제 정의

2.1 현재 운영 현황

현재 백엔드 서버는 데이터베이스가 없는 프록시 구조이다.

  • AI(Claude/Gemini) 호출 중계, 정적 파일 서빙, 토스 결제검증 스텁만 존재
  • 결제 검증 코드에 "실서비스에서는 여기서 DB에 결제 기록 저장"이라는 주석만 있고 실제 저장은 없음
  • 결과적으로 주문·보고서·매출이 어디에도 기록되지 않음

2.2 핵심 문제

문제: 운영 데이터가 적재되지 않아 ①누가 결제했는지 ②얼마를 벌었는지 ③어떤 보고서를 발급했는지 전혀 추적할 수 없다.
영향: 고객이 "보고서를 다시 받고 싶다"고 해도 대응 불가, 환불·정산 근거 부재, 매출/마진 파악 불가.
📌 전제: 어드민 화면을 만들기 전에, 본 서비스가 주문·보고서·AI사용을 저장하기 시작하는 선행 작업(로드맵 Phase 0)이 반드시 필요하다. 데이터가 없으면 어드민은 빈 화면이다.

2.3 어드민 도입 효과

  • 결제·환불 내역을 한눈에 추적 → 고객 응대·정산 가능
  • 보고서 보관·재발급으로 CS(고객 문의) 대응 확보
  • 일/월 매출과 전환율, AI 비용 파악 → 데이터 기반 운영

3. 어드민 목표 및 범위

3.1 목표

  1. 모든 결제 건을 빠짐없이 기록하고 조회·환불할 수 있다.
  2. 발급된 모든 보고서를 보관하고 언제든 다시 조회·재발급할 수 있다.
  3. 매출과 이용 현황을 대시보드 한 화면에서 파악할 수 있다.

3.2 1차 범위 (In Scope)

영역포함 내용
1차 주문·결제 관리주문 목록/검색, 통합 상세(360°), 결제 상태, 환불 처리
1차 매출·이용 통계오늘/이번 달 매출, 주문 건수, 기본 대시보드
1차 보고서 조회·재발급보고서 목록/상세보기, 재발급(재발송), 환불
1차 회원 관리 (신규)회원 목록, 회원 상세(회원 정보 + 구매 이력 + 보고서 + 환불)
1차 운영자 로그인허용된 운영자만 접근(인증)

3.3 범위 외 (Out of Scope — 후순위)

영역사유
후순위 콘텐츠 관리한자 DB 수정·금기 한자·현대명 DB 편집 — 데이터 안정화 후 이관
후순위 운영 설정가격 변경·점검(maintenance) 모드 — 빈도 낮음
후순위 회원 등급/포인트회원 정보 조회는 1차 포함. 등급제·포인트·CRM은 후순위
2차 고급 통계전환율 퍼널·AI 비용 대시보드 — Phase 2로 분리

3.4 성공 지표 (KPI)

  • 결제 누락률 0% (모든 결제가 주문으로 기록)
  • 보고서 재발급 요청 100% 대응 가능
  • 운영자가 5분 내 당일 매출·주문을 확인 가능

4.1 사용자 유형

7. 화면별 상세 기획

7.1 로그인 (F-01)

화면 목적허용된 운영자만 어드민에 진입하도록 인증
구성 요소서비스 로고, 로그인 버튼(이메일 인증), 안내 문구
주요 동작로그인 성공 → 대시보드 이동 / 허용목록 외 → 접근 거부 안내
예외·검증미인증 상태로 내부 URL 직접 접근 시 로그인 화면으로 강제 이동

7.2 대시보드 / 홈 (F-02) — 시각화 강화

화면 목적전체 서비스 현황(매출·주문·환불)을 한눈에 파악. 추이를 그래프로 본다
구간 전환일 / 월 / 연 세그먼트 — 선택에 따라 카드 금액과 그래프가 모두 바뀜
지표 카드선택 구간의 매출 · 주문 건수 · 객단가(ARPU) · 환불액을 금액으로 표시
매출 추이 그래프막대/라인 그래프로 기간별 매출 추이 시각화 (예: 최근 6개월)
보조 영역상품 비중(프리미엄/셀프), 최근 주문 리스트

주요 동작행 클릭 → 통합 상세 / 필터·검색 시 즉시 갱신

7.3.2 ★ 통합 상세 (360° 뷰) — 핵심

흩어진 정보를 한 화면에 모은 핵심 화면. 주문·보고서·회원 어느 탭에서 진입하든 동일한 통합 뷰를 본다.

화면 목적한 화면에서 회원·결제·보고서 확인 + 환불·재발급까지 처리
구성 요소 ① 회원 요약 (이름·연락처·로그인수단·가입일) — 회원 상세로 이동 링크
② 결제·주문 정보 (금액·결제수단·토스 주문번호·시각) + 상태 배지
③ 연결 보고서 (이름·한자·점수, [보기]·[재발급])
④ 액션 [환불 처리] · [보고서 재발급]
주요 동작[환불] → 확인 모달 → 토스 환불 API → 상태 '환불' 갱신·시각 기록 / [재발급] → 보고서 재발송
예외·검증이미 환불된 주문은 [환불] 비활성화 / 환불 실패 시 사유 노출, 상태 변경 없음
⚠️ 보안: 환불은 실제 송금이 발생하는 작업이다. 토스 시크릿키는 브라우저에 두지 않고 서버 함수에서만 호출하며, 환불 실행은 항상 운영자가 직접 클릭하여 수행한다(자동 환불 금지). 모든 환불은 로그로 남긴다.

7.4.1 보고서 목록

테이블 컬럼발급일시 · 이름(한글/한자) · 점수 · 연결 주문 · (상세 링크)

7.4.2 보고서 상세 + 재발급 + 환불 + 디어네임 열기

화면 목적보고서의 핵심 일부를 빠르게 확인하고 재발송·환불. 전체는 본 서비스에서 확인
표시 내용저장된 report_json에서 핵심만 발췌(이름·점수·핵심 메시지·요약). 어드민에 전체 본문을 다 그리지 않음
구성 요소핵심 일부 패널, 연결 주문·회원 정보, [재발급] · [환불] · [디어네임에서 열기] 버튼
디어네임 열기[디어네임에서 열기 ↗] → 본 서비스의 실제 보고서 화면을 새 탭으로 열어 전체 내용을 그대로 확인
주요 동작[재발급] 재발송 / [환불] 연결 주문 환불 / [디어네임에서 열기] 본 서비스 이동

7.5 회원 관리 (F-13 · F-14) 신규

7.5.1 회원 목록

② 구매 이력 테이블 (주문일시·상품·금액·상태) — 각 주문에서 [환불] 가능

📌 통합 관점: 회원 상세는 "이 고객이 무엇을 사고, 어떤 보고서를 받았고, 환불이 있었는지"를 한 곳에서 보여준다. 주문·보고서 탭과 같은 통합 상세로 연결되어, 어디서 진입하든 동일한 정보를 본다.

8. 데이터 정의 (기획 관점)

1차 기능을 위해 다음 5종의 데이터를 적재한다. 회원을 중심으로 주문·보고서가 연결된다. (상세 스키마는 구축 계획 문서 참조)

데이터핵심 항목용도
회원(member) 신규가입일, 이름, 연락처, 로그인수단, 구매횟수, 누적결제, 최근주문회원 관리
주문(order)주문일시, 회원(member_id), 상품, 금액, 상태, 토스 결제정보주문·환불 관리
보고서(report)연결 주문, 이름(한글/한자), 생년월일시, 점수, 보고서 전체 내용조회·재발급·디어네임 열기
AI 사용(ai_usage)호출 시각, 종류, 모델, 토큰, 추정 비용비용 모니터링(2차)
감사 로그(audit_log) 신규작업 시각, 운영자, 작업종류, 대상, 부가정보환불 등 민감작업 추적
이벤트(event)단계명, 익명 세션 ID, 시각전환율 통계(2차)

연결 구조: 회원 1 — N 주문 1 — 1 보고서. 통합 상세는 이 연결을 따라 한 화면에 묶어 보여준다.

대시보드 집계: 매출 추이·구간 금액은 orders를 date_trunc('day'|'month'|'year', created_at)로 그룹·합산해 산출(별도 집계 테이블 불필요).

⚠️ 개인정보 주의: 회원 이름·연락처와 보고서의 생년월일시 + 아이 이름은 민감 개인정보다. 최소 수집·운영자 한정 접근·목록 마스킹·보관기간 정책이 필요하다(상세는 9.2).

9. 비기능 요구사항

9.1 보안

  • 운영자 인증 후에만 접근, 허용 이메일 목록 기반
  • 모든 데이터에 행 수준 접근권한(RLS) 적용 — 일반 사용자 조회 불가
  • 토스 시크릿키·서버 전용 키는 환경변수에만 보관, 코드/깃허브 노출 금지
  • 환불·삭제 등 민감 작업은 감사 로그 기록

9.2 개인정보보호 (개인정보보호법 준수)

  • 회원 이름·연락처, 아이 이름·생년월일시는 최소 수집, 서비스 제공 목적 외 사용 금지
  • 접근 권한을 운영자로 한정, 목록 화면에서는 이름·연락처 일부 마스킹(예: 김O연, 010-****-1234)
  • 회원 상세 등 민감 개인정보 조회 시 접근 로그 기록
  • 보관기간 정책 수립 및 만료 데이터 파기 절차 마련

9.3 성능 · 가용성

  • 주문/보고서 목록은 페이지네이션으로 대량 데이터에도 빠른 응답
  • 무료 인프라 한도 내 시작, 트래픽 증가 시 유료 플랜으로 단계적 승급

9.4 환불·민감작업 기술 적용 중요

환불은 실제 송금이 발생한다. 어드민 화면(브라우저)에서 토스 API를 직접 부르지 않고, 반드시 서버 함수를 거친다.
